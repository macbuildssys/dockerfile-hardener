# DH003 — ShellTools

**Severity:** 🟠 HIGH
**Auto-fix:** ✗ No
**Tags:** CIS-DI-0007, Docker-Hardening, Attack-Surface

---

## What this rule checks

Shell, network, and debugging tools must not be installed in the final
production stage. Specifically flagged packages include:

| Category | Packages |
|---|---|
| Shells | `bash`, `sh`, `zsh` |
| Network | `curl`, `wget`, `nc`, `netcat`, `ncat`, `socat`, `telnet`, `ftp` |
| Scanners | `nmap`, `tcpdump` |
| Debuggers | `strace`, `ltrace`, `gdb` |
| Editors | `vim`, `nano`, `emacs` |
| Compilers | `gcc`, `g++`, `make` |
| Remote access | `ssh`, `sshd` |
| Interpreters | `python`, `perl`, `ruby` (when not the app runtime) |

---

## Why it matters

These tools are the attacker's toolkit. If an attacker gains code execution
inside your container — through an application vulnerability, a deserialization
flaw, or an injected dependency — they will immediately look for these tools to:

- Exfiltrate secrets via `curl` or `wget`
- Establish persistence via `bash` or `ssh`
- Probe the internal network with `nmap` or `nc`
- Escalate privileges with `strace` or `gdb`

Removing them does not prevent every attack, but it removes the easiest
pivot points and forces an attacker to bring their own tooling — which is
detectable.

This directly implements the Docker Hardened Images principle of removing
shells and debugging tools from production images.

---

## Failing example

```dockerfile
FROM ubuntu:22.04
RUN apt-get update && apt-get install -y \
    myapp \
    curl \
    bash \
    vim
CMD ["myapp"]
```

---

## Passing example

Multi-stage build — tools in builder, nothing in runtime:

```dockerfile
FROM ubuntu:22.04 AS builder
RUN apt-get update && apt-get install -y curl gcc make
RUN curl -fsSL https://example.com/src.tar.gz | tar xz
RUN make

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /out/myapp /myapp
CMD ["/myapp"]
```

---

## Note on build stages

This rule only flags the **final** stage. Build stages are expected to use
compilers, network tools, and package managers — that is their purpose.
Only the stage that produces the runtime image is checked.
