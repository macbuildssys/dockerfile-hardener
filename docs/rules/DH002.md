# DH002 — LatestTag

**Severity:** 🟠 HIGH
**Auto-fix:** ✗ No
**Tags:** CIS-DI-0006, Docker-Hardening, Supply-Chain

---

## What this rule checks

Every `FROM` instruction must reference a specific, pinned image tag or a
digest (`@sha256:...`). Images pulled with `:latest` or with no tag at all
are resolved at build time to whatever the registry currently holds under
that name — which can change without notice.

---

## Why it matters

Using `:latest` breaks three things:

**Reproducibility** — rebuilding the same Dockerfile next week may pull a
different image, producing a different output binary with different
dependencies and a different vulnerability profile.

**Auditability** — you cannot tell from the Dockerfile alone which exact
image version was used in a given build.

**Supply chain security** — a compromised or maliciously updated upstream
image tagged `:latest` will silently be incorporated into your next build.

A digest pin (`@sha256:...`) is the strongest form because it is
cryptographically bound to a specific image manifest. A version tag
(`:1.2.3`) is acceptable for most workflows.

---

## Failing examples

```dockerfile
FROM ubuntu                  # no tag — resolves to :latest
FROM ubuntu:latest           # explicit :latest
FROM node:lts                # mutable "rolling" tag
```

---

## Passing examples

```dockerfile
FROM ubuntu:22.04
FROM python:3.12.3-slim
FROM gcr.io/distroless/static-debian12:nonroot
FROM ubuntu@sha256:a1b2c3d4e5f6...   # strongest form
```

---

## Multi-stage builds

Every `FROM` in a multi-stage build is checked independently. Both the
builder and the runtime stage must pin their tags.

```dockerfile
FROM golang:1.22.2 AS builder   # ✔ pinned
FROM gcr.io/distroless/static-debian12:nonroot  # ✔ pinned
```

---

## Why auto-fix is not available

The correct pin depends on what the current registry resolves to, which
requires a live network call. `dockerfile-hardener` is a static analyser and
does not make network requests. Look up the current digest with:

```bash
docker inspect --format='{{index .RepoDigests 0}}' ubuntu:22.04
# ubuntu@sha256:a1b2c3...
```

Or use `docker buildx imagetools inspect ubuntu:22.04` for a detailed view.
