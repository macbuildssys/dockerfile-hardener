# DH001 — RootUser

**Severity:** 🔴 CRITICAL
**Auto-fix:** ✔ Yes
**Tags:** CIS-DI-0001, OWASP-A05, Docker-Hardening

---

## What this rule checks

The final build stage must set a non-root `USER` instruction before `CMD` or
`ENTRYPOINT`. If no `USER` is set, or if `USER root` / `USER 0` is explicitly
used, the container process runs with full root privileges.

---

## Why it matters

Docker containers share the host kernel. A process running as root inside a
container that escapes its isolation — via a kernel exploit, a misconfigured
volume mount, or a container runtime vulnerability — gains root on the host.

Running as a non-root user is the single most effective mitigation against
container breakout being immediately catastrophic.

It also satisfies:
- **CIS Docker Benchmark 4.1** — do not run containers as root
- **OWASP A05:2021** — Security Misconfiguration

---

## Failing example

```dockerfile
FROM ubuntu:22.04
RUN apt-get update && apt-get install -y myapp
CMD ["myapp"]
# No USER instruction — defaults to root
```

```dockerfile
FROM ubuntu:22.04
USER root          # Explicit root — still flagged
CMD ["myapp"]
```

---

## Passing example

```dockerfile
FROM ubuntu:22.04

RUN apt-get update && apt-get install -y myapp \
    && groupadd --gid 65532 nonroot \
    && useradd --uid 65532 --gid nonroot --no-create-home nonroot

USER nonroot
CMD ["myapp"]
```

For distroless images, the `nonroot` user is pre-created:

```dockerfile
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /app /app
# nonroot user is already set by the :nonroot tag variant
CMD ["/app"]
```

---

## Auto-fix behaviour

When `--fix` is run, `dockerfile-hardener` inserts `USER nonroot` immediately
before the last `CMD` or `ENTRYPOINT` instruction. Review the result — you may
need to create the `nonroot` user in a `RUN` step first if the base image does
not include it.
